# 项目文档去 AI 味参考

这份参考结合了用户提供的 `packtide · systide` 文档样本和近期读取的中文去 AI 味 Skill。它描述编辑信号，不判断作者身份。

## 1. 抽象管理词堆叠

常见高风险词包括：

- 契约、矩阵、门禁；
- 路由、编排、链路、闭环、抓手、底层逻辑；
- 作用域、边界、能力、机制、身份、治理；
- 类型化、可观察、可移植、可验证、职责清晰、明确、完整、精确。

这些词在真实技术语境里有用。问题在于它们没有具体对象和动作，只是给句子加上管理或技术色彩。

```text
AI 味：发布门禁确保能力边界和验证矩阵的一致性。
更清楚：发布前运行这 4 个检查：格式、测试、二进制、安装脚本。任一检查失败就停止发布。
```

处理时问：“谁对什么做了什么？”如果词语没有指向文件、命令、检查、权限、数据结构或流程，就换成普通词，或直接删掉。

## 2. 文档写成代码

常见症状：

- 页面充满字段名、伪 schema、参数行、类型名和代码块；
- 每个说明都写成“字段：解释”或“对象：属性”；
- 代码示例多于解释，读者看完仍不知道什么时候使用；
- README、API reference、设计文档和测试报告套用同一种结构；
- HTML 布局、徽章、目录和层级装饰制造了“完整感”，却没有改善查找。

代码、字段、表格和徽章本身没有问题。问题是格式替代了说明，或同一事实在表格、段落和列表中重复。

处理顺序：

1. 先说读者要完成什么；
2. 再说机制、前置条件和限制；
3. 最后给出必要的命令、字段或代码示例；
4. 删除只重复标题或字段名的解释；
5. 把 API/reference 细节移到专门的 reference 文档，不要让 README 承担所有内容。

## 3. 中英文和术语层级混杂

常见症状：

- 中文句子里突然出现没有必要的英文短语；
- 同一概念在不同段落叫后端、提供方、软件源、backend；
- 英文缩写、中文翻译、代码标识符没有区分；
- 英文词只是为了显得专业，并没有增加信息。

处理时：

- 保留 API、命令、字段名、产品名、协议名和没有精确中文译法的词；
- 普通说明统一使用目标语言；
- 首次出现时解释必要术语，之后使用一种写法；
- 检查大小写、空格、连字符、品牌官方写法和中文标点。

## 4. 功能概述里的三项包装

高风险句子会把多个抽象形容词、数量词和职责标签压进开头：

```text
一套类型安全的后端、两个职责清晰的命令行工具，以及基于 fzf 的快速交互流程……
```

这类句子通常同时承担产品定位、架构介绍和营销口号，信息层级混在一起。

处理时先说工具解决什么问题；架构放到后文；删除没有证据的形容词，例如“快速”“清晰”“类型安全”。数量确实重要时，单独说明数量和各自职责。

## 5. 同一事实跨章节重复

同一行为可能先出现在“功能”，又出现在“安装”，然后在“支持后端”“运行依赖”“验证边界”里换一套词再说一遍。

给每条事实指定一个主位置：

- “功能”说用户能做什么；
- “安装”说如何安装；
- “支持”说兼容范围；
- “验证”说如何证明。

其他章节只保留读者需要的差异或链接，不要互相复述。

## 6. 时间敏感信息混入常青文档

README 中的注册状态、临时政策、某日完成的命名检查、当前发布状态或一次性的环境结论，可能很快失效。

当前状态要带日期和来源。临时公告移到 changelog、release note、migration 或 FAQ。没有长期价值的过程记录不要放进安装主流程；一次检查的结果也不要写成永久保证。

## 7. 条件和例外塞进长句

大量“仅在……时”“如果……则……”“发现……就……”“未知……仍然……”会把主动作淹没。

一个句子先说主动作；分支条件用列表、表格或独立句；分开写致命失败、可选失败和警告。不要为了显示所有边界，把一个用户动作写成半页条件句。

## 8. 合法边界写成防御性声明

安全、权限、包管理器和发布文档确实需要边界。问题通常是同一限制在多个章节重复，或把所有可能的异常塞进正文。

保留会改变用户行为的警告。把安全细节放入 SECURITY.md，把贡献检查放入 CONTRIBUTING.md，把发布条件放入 release 文档。README 只保留安装和运行必须知道的边界。用具体动作和结果替代“保持可观察”“确保一致性”“不会静默通过”等抽象保证。

## 9. 形容词超载

这些词经常成簇出现：

- 类型安全、职责清晰、快速、完整、精确、明确、可移植、可选、原生、可信、独立、可观察；
- 强大、先进、可靠、灵活、无缝、全面。

把形容词换成可检查的事实：

```text
“可观察的失败诊断”
→ “命令保留 stderr 和退出码，并写入诊断文件。”

“明确的命令计划”
→ “先生成 argv，再显示给用户确认。”
```

如果没有对应事实，就删掉形容词。

## 10. 不自然的技术汉语

项目文档可能同时有 AI 腔和翻译腔：

- “本地化整个流程”可能只是“根据语言设置显示提示”；
- “报告每个事务”可能只是“报告每次操作”；
- “可选软件包行”可能应为“可选软件包条目”；
- “接受特权事务”可能应为“执行特权操作”；
- “原生更新”可能需要改成“发行版自带的更新命令”。

不要机械替换。先确定动作、对象和责任，再用目标语言的普通技术表达重写。

## 11. 组合信号

以下组合比单个词更值得处理：

- 抽象产品定位 + 三项并列 + 大量形容词；
- 功能列表 + 支持矩阵 + 运行依赖重复相同能力；
- HTML 布局、徽章、目录和多级标题同时出现，却没有改善查找；
- 英文术语、中文翻译和代码字段混在同一句；
- 每个失败分支都写进一个长句；
- 同一限制在 README、SECURITY、CONTRIBUTING 中重复；
- “契约 / 矩阵 / 门禁 / 边界 / 能力 / 路由”连续出现，却没有对应命令或文件；
- 时间敏感事实和永久安装说明混在一起。

这些信号不要求删除技术细节。目标是把信息放回合适的文档层级，让每个术语、表格和代码块承担明确职责。
